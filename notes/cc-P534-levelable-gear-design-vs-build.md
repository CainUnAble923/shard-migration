# P534: levelable gear design versus the build

Checked October 24, 2026. Notes only.

The item level engine is in main. It can seal crafted weapons, armor, shields, and jewelry, award combat XP, and spend points on properties. It is not a complete player progression feature: the seal has no normal player source, accepted XP rules differ from the code, reset dormancy is missing, and milestone procs are not built. Chase rejected sockets on October 22. Sockets are outside the backlog for this feature.

## Questions that still need a concrete answer

These are recommendations for review, not new Chase decisions. Acquisition method, death payout, tradeability, dormancy, milestone procs, and no sockets are already chosen. Their missing implementation should not cause another round of asking the original either/or questions.

| Question or conflict | Recommended answer |
| --- | --- |
| Which contributor and XP curve rules should replace the conflicting implementation? | Honor October 18: full credit at 10 percent of victim maximum HP, including owned helpers, and the `13 x n^1.4` transition table. Reconcile the start-level convention explicitly. P261's damage splitting and quadratic curve are current behavior, not evidence that the earlier answers were revoked. |
| Should the displayed creature level also determine the item award and creature floor? | Yes. Call `ClusterFCreatureLevels.Level`, then apply contributor qualification, the per-item floor, configured multiplier, and caps. Do not call the capped bard calculation and label it the displayed level. Tune using actual kill samples. |
| What numeric rate and presence limits should apply? | Keep the accepted floor. Start testing a configurable limit of 10 qualifying death awards per item in a rolling 60 seconds, with excess awards discarded rather than banked. This is an unmeasured proposed default, to tune against actual encounter rates. Require the credited player on the same map and within the chosen encounter reward range at death; use the same rule for helper-earned owner XP. Both the number and presence rule are recommendations, not already approved values; P482 finding 4 motivates the presence check. |
| How should defensive-only participation qualify? | Support a wearer or companion that took meaningful damage from the victim, consistent with C.2, while preventing trivial tagging. Require a documented contribution threshold. Keep death-paid XP; do not introduce a per-hit payment farm. Exact defensive qualification remains a design choice. |
| What makes the unlock and consumable obtainable? | Retain the accepted League quest once per character and a crafter-made consumable per item. Specify quest prerequisites, repeat behavior, recipe skill, materials, and each material's source in one build prompt. Apply the unlock check when sealing, not on later trades. Rename the displayed consumable to Bonding Oil to avoid confusion with Smith Seals currency; the existing type need not be renamed. Recipe numbers remain unchosen. |
| Which item families should the first player release support? | Keep weapons, armor, shields, and jewelry for the first coherent release. Resolve P72's clothing inclusion explicitly before describing all crafted equipment as supported. Schedule crafted caster/bard item families only with real craft sources and useful effects; do not accept a base type that can never earn or use XP. |
| Which point budget and prices should ship? | Evaluate P72's material-sensitive budget and exceptional x1.5 budget as one table, alongside the chosen XP curve and imbuing ceilings. Keep one shared property count across imbuing and level spending, with an explicit treatment of guild-expanded slots. Current 880-point earnings and prices are internally scaled together; replacing only one side is not a safe tuning change. |
| Does material Luck count against a per-item ceiling? | Yes if the promise remains an effective per-item maximum. Include material contribution in the existing-value calculation. Otherwise explicitly narrow the promise to enchanted Luck and obtain approval for the extra material allowance. P482's arithmetic is a source finding, not a measured client outcome. |
| How can dormancy know which purchases were earned above acting level? | Add a versioned purchase ledger containing property, amount, unlock level, and paid cost, then apply only purchases within acting level. Keep base crafted properties unchanged and the item wearable. Define a deterministic conversion for any existing aggregate-only records before rollout. Do not claim historical purchase order can be reconstructed from a dictionary of totals. If a simpler proportional rule is preferred, approve it as a design change first. |
| What is the acting-level and companion rule? | Use `min(item level, wearer current level + Arms Lore margin)` with the accepted +5 at Arms Lore 100 and +10 at 200. Use the companion owner's current level and attunement for its gear. Limit new item progression to the current wearer's permanent loop maximum, retaining previously earned item levels across a trade or reset. All require the actual F-12 level service rather than con-color's best-skill placeholder. |
| Does Echo of the Loop affect item XP? | Keep automatic player re-climb echo out because items do not reset. Make the explicitly named imbue property a separately capped item-XP modifier, matching its promised purpose, only after approval. `S/server/customizations/Imbuing/ClusterFImbueEffects.cs:443-446` exposes the unused percentage hook. P72 and the imbue description disagree; this remains open. |
| Which proc, at which milestone, and how many may act? | Begin with one selected proc per item, unlocked at item level 100, bought explicitly with item points. This level and limit are proposals. Use a small approved effect list, a shared per-wearer cooldown, no proc chaining, and no gold/resource creation. Specify helper ownership and trade behavior, and make the proc dormant below its acting-level unlock. Build on the registry and spending UI, with explicit combat dispatch. Do not add sockets, accessory charms, or unrestricted weapon-effect purchases. |
| How should respec refund purchases after tuning? | Charge a fixed approved fee and refund saved purchase-time costs, preserving XP and item level. Decide whether the selected proc can also be changed. Reuse the purchase ledger needed for dormancy rather than recalculating old purchases at today's prices. |

Dormancy is the largest data gap. Engine:216-217 stores `Dictionary<string, int> Bought`, and :271-275 serializes only key/value pairs. It records neither purchase order, unlock level, nor paid cost. A reader can clamp a numeric bonus against today's property ceiling, but it cannot determine which part was bought during the first N item levels. P261's suggestion that dormancy will be one test in `EffectiveBonus` understates the accepted rule's implementation cost.

## Suggested build order

1. Fix the real pet-death path and shared slot counting, integrate active extra accessories, and settle material Luck. Preserve the existing item serial and base properties. Give each regression a failing run before its fix.
2. Align contributor awards, creature level input, curve, points/prices, and anti-farm controls. Decide how any existing test-item XP and purchases are carried forward. Presence and defensive participation rules belong in this pass.
3. Build versioned purchase records and actual F-12 current/max-level integration. Implement owner-based companion dormancy, acting-level display, and progression limits. The underlying player level/reset service is still unfinished; see [P517](cc-P517-f12-numbers-vs-code.md). `S/server/customizations/Tutorial/ClusterFLoops.cs:40-42` still has the empty reset hook, and con-color's player-level source remains provisional.
4. Add a narrow, explicitly purchased milestone proc with its saved state and runtime trigger. Decide its cost alongside the revised point budget. The bonus-point milestone already present can remain a separate rule if approved.
5. Finish and validate the accepted League unlock and crafted consumable acquisition, including recipe/resource reachability. Release to players only after the progression and abuse rules above are coherent. Add paid respec when its refund data and economy are ready. No socket work belongs in these steps.

These are suggested task boundaries. This report does not authorize code changes, a deployment, or a new decision in `docs/`.
