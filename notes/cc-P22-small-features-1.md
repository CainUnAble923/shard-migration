## 2. F-19: the bank holds 1,000 items

### 2.1 Facts, confirmed

- `Server/Items/Containers.cs:7-23`: `BankBox` is a core type with `DefaultMaxWeight => 0` (`:23`), so it has no
  weight limit. It does not override `DefaultMaxItems`.
- `Server/Items/Container.cs:154` `DefaultMaxItems => GlobalMaxItems`; `:159` `GlobalMaxItems = 125`.
  `:85-103`: `MaxItems` is per container, falls back to the default while `_maxItems == -1`, and is saved only when
  set (`ShouldSerializeMaxItems`, `:99-100`).
- `Container.CheckHold` (`:212-251`) counts `TotalItems + item.TotalItems + 1` (`:226-229`). `TotalItems` includes

  `SendFullItemsMessage` (`:265-269`): cliloc **1080017**.
- `Server/Mobiles/Mobile.cs:1593-1609`: the `BankBox` getter creates the bank on first use.
  `FindBankNoCreate` (`:7416-7424`) does not create it.

### 2.2 How the limit reaches the bank, and why

**Set `MaxItems` on the bank box at world load and at login.** No patch. `ClusterFBankLimit.cs`:

- `GetMaxItems(owner) = BaseItems (1000) + LeagueRankBonus(owner)`: the one function that decides the number.
- `LeagueRankBonus` returns 0, with a comment naming F-12 and F-19. `ItemsPerLeagueRank = 100` is recorded beside it.
- `ApplyToLoadedPlayers` (world load): every `PlayerMobile` whose bank exists. It does not create banks.
- `OnLogin` (`[OnEvent(PlayerLoginEvent)]`, the hook `ClusterFStatCaps` uses): creates the bank if missing.

Why not override `DefaultMaxItems`: `BankBox` lives in the core (`Server`) assembly, so a partial from UOContent
cannot add to it, and `MaxItems` is not virtual. The only other way is a core patch, and the policy allows a patch
only where no hook reaches; here the login and world-load hooks do. The cost: the number is saved on each bank, so
a Game Master's hand-set `MaxItems` on a bank is overwritten at the next login or world load. When F-12 ranks exist,
a rank change should call `ClusterFBankLimit.Apply(m, true)` so the bank follows at once. `GlobalMaxItems` is never
touched.

### 4.3 Part B: `GuildResources.cs`

- `GuildCost.Of(type, amount)` matches as pinned does (`IsInstanceOfType`); `GuildCost.Where(predicate, amount)`
  matches specific items.
- `Candidates(pm, cost)`: the order items are taken in. **pack outside satchels, pack inside satchels, bank outside
  satchels, bank inside satchels**, each breadth first. Never searched: equipped items (only the pack and bank are
  walked). Never taken: blessed (`LootType.Blessed` or `BlessedFor`), anything inside an `ILockable { Locked: true }`
  or a secure or locked-down container, and a container that still holds anything.
- `TryConsume(pm, costs...)`: plans every cost item by item before taking anything, and reserves what it has
  promised, so two costs on the same items cannot double count (fact 6 tests this). If anything is short, nothing is
  taken.
- `TryPay(pm, guild, scripKey, scrip, scripName, gold, materials...)`: the price of any upgrade or restoration. It
  checks scrip, each material (with "You need 60 valorite ingots in your backpack or bank (you have 45: 20 in pack, 25
  in bank)") and gold, then takes materials, gold and scrip. `CanPay` is the same check, for a button's colour.
- `Describe` and `DescribeAll` give the gump lines: "60 valorite ingots: 20 in pack, 40 in bank" when there is
  enough, "60 valorite ingots: have 45 (20 in pack, 25 in bank)" when not. Shown on the restoration, satchel upgrade,
  four pickaxe upgrade and hammer gumps; the work order ledger shows "(n pack, m bank)" on met lines.
- F-16's new prices go through it (`GetRestoreCost` feeds `TryPay`).

### 4.4 For Chase: one ordering choice

Chase's rules are "pack first, then bank" and "loose first, then satchels". They agree except in one case: a
satchel in the **pack** versus loose stock in the **bank**. I put pack before bank as the outer rule, which uses
what you brought before what you stored. The other reading is that all loose stock goes first, so sorted stock is
always used last. Both are one list in `Candidates`. Switching means swapping two lines, and test 6 changes with
it.

### 5.2 Built

- `BODCombineContained.cs`: `Begin(from, deed)` opens the cursor. `Combine(from, deed, target)` takes every item
  **directly** in the targeted container (for a large deed, every `SmallBOD`) and runs it through the deed's own
  `EndCombine`; pinned's checks and messages are unchanged and items that fail stay put. It stops when `deed.Complete`
  and says "N items were combined with the deed".
- **The backpack itself is accepted.** ServUO's only test is `targeted is Container`. OSI's wording ("a pack within
  your back pack") describes the usual case, not a refusal.
- **The container must be the backpack or inside it** (1045158 otherwise). ServUO does not check this. Without it, a
  bag in the bank, or on the ground, would feed the deed, because `EndCombine` does not check and pinned enforces
  "in your backpack" only in `BODTarget`.
- Smith BODs at the Blacksmith Guildmaster are pinned's `SmallSmithBOD`/`LargeSmithBOD` (our `patches\LargeSmithBOD.cs`
  replacement does not touch the gump), so the button appears there with no extra work. The same goes for tailor
  deeds.

### 5.3 How the button gets in: one patch (`server\patches\BOD-combine-contained.patch`)

The alternatives were weighed before patching, as AGENTS.md asks:

- **Partial:** neither gump is declared `partial`, and a partial could not add a row to `BuildLayout` anyway.
- **Subclass:** the gumps are created with `new SmallBODGump(...)` inside pinned code, in `SmallBOD.OnDoubleClick`
  (`:85`), `SmallBOD.EndCombine` (`:160`), the gump's own response (`:80`), and the same three in `LargeBOD`. Every
  one of those would need a patch or an override, and `EndCombine`'s cannot be overridden without copying it. That
  is copied upstream logic, which the policy ranks below a failing patch.
- **Patch, chosen.** Each gump grows one row (24 px). The new button (reply 3, cliloc 1157304) sits above EXIT, and
  one `else if` branch calls `BODCombineContained.Begin`. 51 changed or added lines across the two files; the
  logic is in customizations. `apply_patch` line in `docker\uo\apply-patches.sh` with the reason. Applied with
  `--fuzz=0`.

## 6. F-15: date version and patch notes

### 6.1 Part A

1. **`bulletins.txt` is not in the image.** `Configuration` is bind-mounted from the host:
   `${SERVER_PATH}/uo/modernuo/Configuration` on live, `Configuration-test` on the test shard
   (`docker\uo\docker-compose.yml:18`, `docker-compose.test.yml:39`). `ClusterFBulletinSystem` reads it only on
   `[ClusterFBulletin load` (`ClusterFBulletin.cs:217-290` HEAD), so it **must be loaded by hand**. A version can post
   itself on start only from something that ships with the build, which is what F-15 does: `CHANGELOG.md` and
   `VERSION` are copied into the image (`docker\uo\Dockerfile`, runtime stage, to `/modernuo/Data/ShatteredLegacy/`;
   `Core.BaseDirectory` is the `WORKDIR` `/modernuo`) and read in `ShardVersion.Configure`.
2. **TazUO honors the open-URL packet and does not ask.** Pinned `Mobile.LaunchBrowser` (`Server/Mobiles/Mobile.cs:7812`)
   -> `NetState.LaunchBrowser` (`Server/Network/NetState/NetState.cs:407-411`). That sends cliloc 501231 as a label,
   then packet **0xA5** with the URL (`Server/Network/Packets/OutgoingPlayerPackets.cs:178-191`). TazUO
   (github.com/PlayTazUO/TazUO, `main`, read 2026-10-01): `src/ClassicUO.Client/Network/PacketHandlers/OpenUrl.cs`
   calls `PlatformHelper.LaunchBrowser(url)`. That validates the scheme (http, https or file) and opens it with
   `Process.Start` (shell execute on Windows), with **no confirmation**. This is the `main` branch, not necessarily
   the build players have installed.
3. **The wiki** is DokuWiki in `sl-wiki` on Haven. Pages are files under `/storage/data/pages` (named volume
   `sl-wiki-storage`; `D:\UO\haven-migration\haven-wiki-update.sh`), and the site's pages are in namespace `uo`
   (`/uo:start`, `/uo:connection`). **Heading anchors:** DokuWiki `inc/pageutils.php` `sectionID` runs
   `cleanID` (lowercase; specials, including the space, become the separator `_`) and then
   `str_replace([':', '.'], '', ...)`. So **dots are dropped**. A heading of only digits becomes "section" plus its
   digits. Hence the heading is "Version 2026.09.30", whose anchor is `version_20260930`, and `2026.09.30.2` is
   `version_202609302`. Read from DokuWiki `master` on GitHub. The live wiki is not checked for a heading with dots
   in it; Chase's publish step confirms it.
4. **status.json** is built in `ShardStatusPublisher.Render` (`server\customizations\ShardStatusPublisher.cs:186-241`).
   The test shard has no status mount (`docker-compose.test.yml:37-41`), so its publisher writes nowhere.

### 6.2 Built

- **`CHANGELOG.md`**: the format explained at the top in an HTML comment (ignored by the parser), **no version
  sections**, as the brief says. **`VERSION`**: empty. So the build has no version: nothing posts, `[version` says so,
  and `shard.version` is null.
- **`ShardVersion.cs`**:
  - `PatchNotes.Parse`: "## 2026.09.30" starts a version, "### Added/Changed/Fixed" its lists, "- " items. HTML
    comments and anything else are ignored; it never throws.

  - `ShardVersion.Load(changelog, VERSION)`: VERSION wins when it is a date version; otherwise the newest section. A
    mismatch or a VERSION with no section is reported on the console.
  - `Configure` reads both from the image, logs the version, writes the rendered page to
    `/modernuo/Data/ShatteredLegacy/patch_notes.txt` in the container, and registers `[version` (Player).
- **Run at server start, not build time.** One parser, in C#, gated by the shard's own tests. The notes in the image
  are exactly the build's notes. No generated source is committed. A build-time generator would have needed a
  second parser (PowerShell or Python) that `build.sh`'s test gate cannot run.
- **Bulletin** (`ClusterFBulletin.cs`): `OnLogin` now also asks `ShardVersion.UnseenNotesFor(acct)`. The gump shows
  "Shattered Legacy <version>", the short list (8 lines, then "... and N more"), and **Full notes (opens the wiki in
  your browser)** (button 2, `LaunchBrowser`), above any unread bulletins. Any response marks the version seen.
  **Per account, once per version, with no saved type changed:** the seen version is
  `FlagValues["bulletin.seenVersion"]`, an existing saved string map on `ClusterFAccountData`. No version bump was
  needed.
- **`[version`**: "Shattered Legacy <version>" and the notes gump again; or "has no version number yet" / "no notes
  for this version".
- **status.json**: `shard.version` (string, or null). Schema stays 1 (an added field). Contract line added to
  `docker\uo-status\README.md`; P6's test updated.
- **`scripts\Publish-PatchNotes.ps1`** (PowerShell 5.1, parse-checked): reads the page and VERSION from the running
  container (`sl-modernuo-test` by default), shows them, compares with the wiki's current page over SSH, and only with
